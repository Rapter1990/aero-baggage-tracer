# ADR 0004: Search read models and rebuild

Status: proposed (search-service, issue #13; follow-ups #28 and #29, built, and a bullet in #15)

## Context

The search-service answers "find a bag or a case" and the airport report from Elasticsearch. Elasticsearch is a read model: it must be rebuildable from the services that own the data (AT-18, "Rebuild Elasticsearch from source data with no duplicate documents"), without touching them.

A review of the code before the build found four gaps:

1. **No durable source.** Every topic is `cleanup.policy=delete` with 7-day retention (`docker-compose.yml`), and the journey and recovery outboxes are purged. A rebuild from Kafka alone is silently incomplete after a week. Reading another service's database is forbidden (one schema per service).
2. **The filters are not in the events.** `CaseChangedPayload` carries `caseId, bagTag, legId, state, version, reason`; `RiskChangedPayload` carries `bagTag, legId, previous, current, departureAt`; `ScanReceivedPayload` has the scan airport, `legId`, `flightNumber`, `departureAt`. No event has the airline, the leg's origin and destination, or the case's `openedAt` and `resolvedAt`. The airline exists nowhere in the system.
3. **No search-side ownership.** No event carries `passengerRef`, so search cannot apply journey's passenger ownership rule (AT-15).
4. **No Elasticsearch in Compose**, and the gateway routes only `/api/v1/reports/**` to the search-service.

## Decision

1. **Rebuild sources (AT-18).** Each owning service exports its own current state through an internal, read-only, keyset-paged endpoint (`GET /internal/v1/export/...?after=&size=`), authenticated with a service token like capacity's `X-Service-Token`, and with no gateway route: journey-service exports bags with their legs (#28), recovery-service exports cases with `version`, `openedAt` and `resolvedAt` (#29). Risk level has no database owner (risk-streams keeps it in a KTable), so `baggage.risk.changed.v1` becomes `cleanup.policy=compact,delete` with a long retention (its key `bagTag:legId` suits compaction; #15) and a rebuild replays it from offset 0. A rebuild never reads another service's database and never relies on the 7-day topics. **Accepted limit:** hourly risk history older than the retention window cannot be rebuilt.
2. **"Source untouched" means** the reconciler issues only `GET`s and consumes only from Kafka; it writes nothing to the source schemas, their outboxes or Kafka topics; source row counts and checksums are identical before and after.
3. **Events.** No enrichment calls from the search-service. The producers add what consumers need, additively (`EventEnvelope` schema revision, never an edit in place):
   - `CaseChangedPayload` revision 2 adds `openedAt`, `resolvedAt`, `trigger` (`RISK`, `SCANNER_ANOMALY`, `MANUAL`) and `assignedTo`, and `CASE_EVENT_SCHEMA_VERSION` moves from 1 to 2 (#29);
   - journey-service publishes `baggage.bag.registered.v1` (key `bagTag`, added to `Topics.ALL`) with the itinerary snapshot per leg: `legId`, `flightNumber`, `airline`, `origin`, `destination`, `departureAt` (#28). The airline is the validated carrier prefix of the flight number, written down as a rule, not guessed by consumers.
4. **Indexes and ids.**
   - `cases`: one document per case, `_id = caseId`, fed by `recovery.case.changed.v1`. Leg attributes (airport, airline, flight) come from a search-owned leg lookup keyed by `legId`, filled from `baggage.bag.registered.v1`; when the leg arrives after the case, the case is written again with its own version (see "Deviations").
   - `journeys`: one document per bag with nested legs, `_id = bagTag`, fed by `baggage.bag.registered.v1`, `baggage.scan.received.v1` and `baggage.risk.changed.v1`.
   - Strict mapping (`dynamic: strict`) from an index template for `cases-*` and `journeys-*`: `keyword` for `caseId`, `bagTag`, `legId`, `airport`, `airline`, `flightNumber`, `riskLevel`, `state`, `trigger`; `date` (UTC) for the times; `long` for `version`; `resolutionSeconds` stored at indexing time. Free-text `reason` is not indexed at all (see "Deviations"), and no passenger data is indexed.
   - "Risk category" is the leg's `RiskLevel` (`LOW`, `MEDIUM`, `HIGH`), filter name `riskLevel`; the case `trigger` is a separate keyword.
5. **Idempotency without a `processed_event` table** (it cannot share a transaction with an Elasticsearch write, and the service would need a database it otherwise does not):
   - cases: `version_type=external` with `payload.version` (it rises by one on every case event); an Elasticsearch `409 version_conflict` is a successful duplicate, counted as `outcome=stale`, never dead-lettered;
   - journeys: a scripted upsert; the latest scan is replaced only when `(occurredAt, deviceSequence)` is newer (journey's own rule), and a leg's risk only when the event's `occurredAt` is newer (recovery's risk clock). Two topics with unrelated clocks write this document, so one external version cannot work;
   - the offset is committed only after the bulk request is acknowledged, bulk responses are checked per item, transient failures (429, 503, timeout) retry with backoff, and poison records go to `baggage.dead-letter.v1` like recovery's consumers;
   - a case is never deleted (its lifecycle has no delete), so there are no tombstones.
6. **Rebuild without downtime.** Two aliases per index: `cases-read` points to exactly one index; `cases-live` is the set the indexer writes to. Steps: create `cases-vN+1` from the template; add it to `cases-live` (live events now write to both); bulk-load the export (and replay the compacted risk topic for `journeys`) with external versions; check every export page against the new index and compare document counts, recording id checksums (see "Deviations" for what exactly is checked); swap every rebuilt `-read` alias in one atomic `_aliases` call; remove the old index from `cases-live`; delete it only after the longest point-in-time keep-alive has passed. External versions and scripted guards give the same result in any order, so live and snapshot writes may overlap. A rebuild job is started by `POST /api/v1/admin/search/reindex` (ADMIN, `Idempotency-Key`, `202` with a `jobId`, `409 REINDEX_IN_PROGRESS` while one runs).
7. **Reports.** `/api/v1/reports/**` stays in the search-service. Results are eventually consistent: every response carries `indexedThrough` (a watermark) and `lagSeconds`. Buckets are hourly in UTC over a half-open range `[from, to)` with a maximum length (31 days); empty hours are zero-filled; an airport with no data is `200`, not `404`. Counts come from documents with deterministic ids, not from approximate aggregations. Definitions:
   - **risky bags:** distinct bags whose leg had `RiskLevel.HIGH` in the hour of the risk event at that airport (the airport of the leg's origin);
   - **resolved recoveries:** cases whose state is `RESOLVED`, bucketed by `resolvedAt`; `CANCELLED` and `CLOSED_AS_UNRECOVERABLE` are not counted;
   - **mean resolution time:** mean of `resolvedAt - openedAt` in seconds over the cases resolved in the bucket, `null` when there are none; totals are weighted by count;
   - **retries:** cases opened for a bag and leg after an earlier case for the same bag and leg ended in `CANCELLED` or `CLOSED_AS_UNRECOVERABLE`, bucketed by `openedAt`. This is the working definition; change it here before the build if the case study says otherwise (sections 5.4 and 12 are not in the repository, so it could not be checked).
8. **Access.** Search and reports are staff-only: `AGENT`, `DISPATCHER` and `ADMIN` read; `/api/v1/search/index/status` is `DISPATCHER` and `ADMIN`; reindex is `ADMIN`; `PASSENGER` gets `403` everywhere. This keeps `passengerRef` (personal data) out of Elasticsearch. The service enforces the roles itself; the gateway rules are only a coarse edge check. A later decision to open search to passengers needs `passengerRef` on an event (schema revision) and a forced server-side owner filter that ignores client filters, and an AT-15 style test.
9. **Lag.** `search.index.lag` (gauge, seconds) is the consumer-group lag plus the age (`now - publishedAt`) of the last processed batch, zero when caught up (a plain "now minus last `occurredAt`" would grow on an idle topic). Also `search.index.lag.events`, `search.index.events{outcome=indexed|stale|duplicate|failed}`, `search.index.delay`, `search.reindex.runs`, and `GET /api/v1/search/index/status`. The Grafana panel is added with #19.
10. **Elasticsearch runtime.** A pinned image tag in Compose and in the Testcontainers test; Compose runs a single node with `xpack.security.enabled=true`, a password (`ELASTIC_PASSWORD`, a dev-only default in Compose that must be replaced anywhere shared), a heap limit, a named volume, a health check, and port 9200 not published (or bound to loopback in `docker-compose-local.yml`). Spring Data Elasticsearch is used in the search-service in two layers (revised from the first design, which used the plain `co.elastic.clients` client alone): `ElasticsearchRepository` interfaces (`ReindexJobRepository`, `CaseRepository`, `JourneyRepository`) over record documents (`JobDocument`, `LegDocument`, `CaseDocument`, `JourneyDocument`, `createIndex = false`, no `_class` type hint, because the mappings are strict and owned by the index templates) for the job documents and the document counts; and `ElasticsearchOperations` for the bag search (`NativeQuery`, point-in-time, `search_after`), the rebuild's document count and the leg lookup. The leg lookup is a realtime multi-get (`multiGet`) on purpose: a repository's `findAllById` is an ids search, which does not see a leg stored a moment ago, and a case would miss its airport. What a repository cannot say stays on the Java API client that Spring Data wraps: external versioning, scripted and conditional upserts in bulk requests, `op_type=create` and sequence-number conditions of the rebuild lock and idempotency keys, aggregations of the report, and the alias swap (`BulkExecutor`, `ReadModelWriter`, `ReindexJobStore`, `AirportReportService`, `IndexAdmin`). The job documents are read through the repository but written with `ElasticsearchOperations.save`, because a repository's `save` refreshes the index on every call (the auditing callbacks run either way). The job documents are audited (`@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, `@LastModifiedBy`, ADR 0003); the read models are not, because bulk scripted upserts fire no auditing callbacks. Spring Data's `DataAccessException`s are translated like the client's own (503 `SEARCH_UNAVAILABLE` for an unreachable or overloaded cluster). `spring-data-elasticsearch` stays banned in `common-module`, and no Elasticsearch type lives there.
11. **Contract.** `GET /api/v1/search/bags` with optional AND-combined filters `bagTag`, `airport`, `airline`, `flight`, `riskLevel`, `caseState`; `size` default 20, maximum 100, out of range is `400 VALIDATION_ERROR`; sort `updatedAt desc` then a stored `docId` keyword (never `_id`); an opaque, signed cursor over a point-in-time (a forged cursor is `400`, an expired one `410 CURSOR_EXPIRED`); `ApiResponse` envelope with `{items, size, nextCursor, hasMore}`; no raw Elasticsearch hits or scores. New error codes `SEARCH_UNAVAILABLE` (503) and `REINDEX_IN_PROGRESS` (409), thrown with explicit codes (a bare 409 would map to `VERSION_CONFLICT`). The gateway gains `/api/v1/search/**` and `/api/v1/admin/search/**`. The consumer restores the envelope `correlationId` into the logging context and never generates one.

## Deviations in the implementation (#13)

The build differs from the decisions above where review or the code showed a better or a necessary way; each is deliberate:

- **Leg completion without `_update_by_query`.** A case indexed before its leg is written again with `version_type=external_gte` and its own version, not completed by `_update_by_query` (which raises the internal version and would make the next real event look stale). Something indexed before its leg leaves a "waiting" mark in the leg lookup, read with a realtime `mget`, so a registration nothing waits for costs no refresh or search; completion pages through all waiting cases. Risk hours (no version) are completed by `_update_by_query`.
- **A third error code `CURSOR_EXPIRED` (410)** for a cursor whose point-in-time is gone, next to `SEARCH_UNAVAILABLE` and `REINDEX_IN_PROGRESS`; and two more since: `IDEMPOTENCY_KEY_REUSED` (422, a reindex key reused for another scope or by another admin) and `REPORT_TOO_LARGE` (422, a report over its scan cap).
- **The support indexes `search-legs` and `search-risk-hours` are not rebuilt or cleared.** A rebuild writes to them (legs from the bag export, risk hours from the risk topic replay) but never empties them: legs or risk hours whose source records no longer exist stay, so the report can count risk hours whose events have since left the topic. They are single indexes, not alias families.
- **The journey rebuild check, as implemented:** after each bag export page a realtime `mget` checks that every exported bag has its journey in the new index; the job records the number of exported bags, the number missing, and order-independent checksums of the exported and the found bag tags; it fails if any is missing or the new index has fewer journeys than exported bags. It does not compare journey contents (they merge four sources with their own clocks). Cases are checked the same way, at their version or newer.
- **Rebuilt `updatedAt` is derived from owner data**: the latest of the bag's leg departures, latest scan, case `openedAt`/`resolvedAt` and replayed risk events (the export has no event times), so rebuilt journeys never lack it and two rebuilds sort the same.
- **No `reason` is indexed.** The free-text case reason may name people or places and is never a filter; it was dropped from the mapping.
- **The point-in-time is opened lazily**, only when a first page has a next one, with a 1-minute keep-alive: a search that fits one page holds no search context. The snapshot starts just after the first page.
- **Compose image tag.** At the user's request both Compose files name `docker.elastic.co/elasticsearch/elasticsearch:latest`, instead of the pinned tag of decision 10. Elastic publishes no `latest` tag for this image, so the pull fails until a concrete tag (for example `9.5.3`) is set; the Java client and the Testcontainers image stay pinned to 9.2.8.
- **Safety additions to decision 6:** lock renewals and releases are conditional on the holder; a job that loses its lock stops without swapping; the job taking over an expired lease fails the abandoned job and discards its unread indexes; exports must advance, have a page cap, a body-size cap and a job deadline.

## What #28 and #29 changed

The owners' side was built after the search-service, in the same branch; these points refine decisions 1 to 3 and the deviations above:

- **One source of truth for the export and the events.** `common-module` holds the contract: `ExportApi` (paths, `after`/`size`, `size` 1 to 500, a larger or smaller one is `400`), `ExportPage {items, nextAfter}`, `CaseChangedPayload` (a case is exported in exactly the shape of its revision 2 event), `LegSnapshot`, `BagRegisteredPayload` and `BagExport`, and `Topics.BAG_REGISTERED` (in `Topics.ALL`). The search-service's own readers (`CaseChange`, `BagRegistered`, `LegSnapshot`, `SearchTopics.BAG_REGISTERED`) were removed; it reads the export with the tolerant event reader, so a newer owner's enum value reads as `null`.
- **Keyset paging by the owner's own key**: the case id (primary key, PostgreSQL `uuid` order, which is the order of the lowercase text form) and the bag tag (unique, ten digits). `nextAfter` is `null` exactly on the last page (one row more than asked is read to know). Every record that exists for the whole run is returned once whatever is inserted meanwhile; one inserted meanwhile at most once. Both run in a read-only transaction.
- **The service token** is shared code (`ServiceToken`, `ServiceTokenFilter`) and the same header as the capacity-service's. Each owner has a security chain of its own for `/internal/**` that accepts only the token, never a user token (an admin's neither): a missing or wrong one is `401`, the token on another method or internal path `403`. Fail closed: without a token of at least 16 characters every call is `401`, except in the `local` and `dev` profiles, which open the export for local runs (logged at start-up; `test` is not one of them). One setting name for both sides, `SEARCH_EXPORT_SERVICE_TOKEN`. The gateway has no route to `/internal/**` (a test checks every route) and strips `X-Service-Token` on every route to a service that accepts it, journey and recovery included.
- **Revision 2 of `CaseChangedPayload`**: `trigger` is `RISK` (opened from a risk event), `MANUAL` (opened by staff) or `SCANNER_ANOMALY`; no case has `SCANNER_ANOMALY` today, because an anomaly only flags the cases a bag already has. `resolvedAt` is written once, with the move to `RESOLVED`, and is `null` for the other final states. Liquibase `011` adds both columns and backfills existing cases (opened by the system means `RISK`; `resolvedAt` from the history).
- **`baggage.bag.registered.v1`** is queued in the registration's transaction (none for a refused or duplicate one, also under parallel requests). The airline rule is the first two characters of the validated flight number (`^[A-Z0-9]{2}[0-9]{1,4}[A-Z]?$`), decided by the journey-service (`JourneyRules.airlineOf`). Registration times are kept at microseconds, as PostgreSQL stores them, so the event, the row and the export say the same instant.
- **AT-18 end to end**: `RebuildAgainstRealOwnersTest` runs the search-service's real export client and rebuild against the packaged journey- and recovery-service jars (their own processes, a real PostgreSQL, their outboxes publishing to the Kafka the indexer consumes), with Elasticsearch in Testcontainers. The search-service needs the two jars built first; the reactor builds them before it, and the test is skipped locally (fails in CI) without them.
- **Correlation**: the recovery consumers now restore the envelope `correlationId` (shared `CorrelationScope`, also used by the search indexer), so a case opened from a risk event carries the risk event's id. The gap noted under Consequences is closed.
- **Open**: the recovery-service accepts leg ids of at most 32 characters, the journey-service's are 36-character UUIDs, so a risk event for a journey leg is refused there and cases cannot get their leg's airport and airline yet. It needs a decision and a migration of `leg_id` in the recovery-service.

## Consequences

- #13 can pass AT-18 for more than the last 7 days and prove "no duplicates" with a Testcontainer; its text is rewritten accordingly.
- The scope of closed #9 and #11 grows (#28, #29), and #15 gains the compaction and the new topic. #13 cannot be finished before them, and "lag visible in Grafana" waits for #19.
- Journey and case events grow by a few fields; old events read the new fields as `null`, so consumers must tolerate that.
- Hourly risk history older than the compacted topic's retention cannot be rebuilt.
- A search outage never affects the services that own the data: the index is derived and can be dropped and rebuilt.
- Recovery's consumers dropped the correlation id (they never set it in the logging context); the search-service does not repeat that, and #29 closed the gap in the recovery-service.

## Alternatives considered

- **Rebuild from Kafka replay only.** Not durable (7-day retention, purged outboxes); rejected for everything except the compacted risk topic.
- **Read the owning services' databases.** Breaks schema ownership.
- **Enrichment calls from the indexer.** Couples search to the availability of journey and recovery and breaks idempotent replay.
- **A `processed_event` table in a search schema.** Cannot be atomic with Elasticsearch; external versions give the same guarantee.
- **A single write alias for the rebuild.** Allows one write index only, so live events written during the build would be lost.
- **Passenger access with an owner filter.** Needs `passengerRef` in Elasticsearch (personal data) and a second ownership implementation; deferred.
